WebChat 身分綁定流程總覽

一張圖看完三件事：每次開 WebChat 怎麼確認身分、查資料；還沒綁的服務怎麼綁；什麼時候能建立統一 IdP。綁定表由獨立的 IdP 綁定服務保管，直接存各服務會員 PK 的 hash，以 hash 關聯各服務會員表；瀏覽器只經手一次性 code，token 和 hash 都只在後端之間經 Token Exchange 服務傳遞。

與 10/16 版的差異：會員表不新增 idp_id，改為新增自家 PK 的 H(PK) 欄位，以 hash 關聯；開場與補綁都經 Token Exchange 服務，用一次性 code 交接；綁定表改由獨立的 IdP 綁定服務保管；補綁改用彈出視窗（window.open）開各服務自己的獨立授權頁。

01資料流動畫

點一個流程，看資料怎麼在瀏覽器和後端之間移動。藍色標籤是一次性 code 或 challenge，可以經過瀏覽器；綠色標籤是 hash，只在後端之間移動。

02四個原則

瀏覽器只經手一次性 code

平台 token 不離開平台，會員 hash 只在後端之間經 Token Exchange 服務以 S2S 傳遞。瀏覽器經手的只有 code（120 秒、用一次就失效）、challenge，以及 WebChat 的 HttpOnly session cookie。

登入一律在該服務自己的網域

補綁時由 widget 用彈出視窗（window.open）開該服務自己的獨立授權頁，不把登入表單包成元件嵌進平台頁面。登入後也不把 token 存在瀏覽器。

綁定表用 hash 關聯

綁定表由獨立的 IdP 綁定服務保管，一列代表一個人，存各服務用自家 PK 算出的 hash。各服務會員表不寫入 P1，只新增一個 H(PK) 欄位並建索引：S2S 查資料時只帶 hash，服務靠這個欄位才知道是哪個會員。每個服務的 hash 在綁定表只能出現在一列。

P1 不經過瀏覽器

P1 只在 WebChat 後端和 IdP 綁定服務之間以 S2S 傳遞。WebChat 從自己的 session 就知道要綁進哪一列。該服務只回報「登入的是 S1」，不需要知道要綁給誰，流程裡也就沒有能竄改綁定對象的參數。

03誰經手什麼

把總覽圖的步驟攤開成時序，看每一段經過瀏覽器還是後端。

04為什麼不直接把 token（或 hash）交給 WebChat

widget 跑在使用者的瀏覽器上，「後端 → 瀏覽器 → WebChat 後端」這一段一定會經過外網。這段只能讓提貨券（code）通過，不能讓貨（token 或 hash）通過。

面向直接傳 token一次性 code
被偷後能直接打平台 API換不出東西：兌換要 WebChat 的 API Key，Token Exchange 的兌換端點只在內網
暴露時間token 整個有效期，要撐完整個聊天 session120 秒，兌換後立即作廢
重放有效期內出示幾次都收只能用一次；重放一定失敗，並觸發告警
事前作廢已流出就收不回兌換前刪掉即可
稽核沒有交換動作可以記誰寄放、誰兌換、何時，都有紀錄
後端驗證不就擋得住？
驗簽擋得住篡改，擋不住外洩。被偷的 token 完整、有效、沒被改過，平台看到的請求和正常使用一模一樣。要分辨持有者，平台得改用 DPoP 或 mTLS 綁定的 token，就不是平台零改動了。
外洩不就代表整個瀏覽器都不安全了？
很多外洩不必攻破瀏覽器：URL 會進伺服器與 proxy 日誌、Referer、監控工具，使用者也可能把網址貼給客服。這些痕跡留很久，token 在有效期內都能用，code 早就失效。就算瀏覽器真的被攻破，token 能被帶走，在攻擊者自己的機器上用到過期；只拿得到 code 和 HttpOnly cookie 時，攻擊者只能趁頁面開著就地操作。
直接傳，再補上 code 的那些保護呢？
保護靠的是收這串字的端點。token 的收件端是各平台既有的 API，平台不改，就加不了一次性、短效期、驗呼叫方。改請平台發短命、一次性、要先兌換才能用的 token，那其實就是 code。
直接傳 hash 呢？
更不行。hash 不是秘密，也沒有簽章，在瀏覽器裡改掉就能冒充別人。
業界怎麼做？
OAuth 的 Implicit Grant 就是透過瀏覽器直接交 token，RFC 9700（OAuth 2.0 安全最佳實務）建議不要再用，OAuth 2.1 直接移除。標準做法是 Authorization Code，也就是用 code 交換。

05補綁的登入：彈出視窗開該服務網域，不包成元件

「用智生活授權」按鈕放在 WebChat widget 裡，由 widget 用 window.open 開出獨立的瀏覽器視窗，不是頁面內的 modal；手機瀏覽器會開成新分頁，一樣能把結果傳回 widget。授權頁是各服務在自家網域提供的獨立頁面。各平台不需要嵌入其他服務的登入元件，也不需要在自己的網站掛其他服務的登入頁。

為什麼不把登入表單包成元件嵌進平台

  • 帳密會輸入在宿主頁上，宿主頁的所有 JS（包括第三方 script 和 XSS）都讀得到。
  • 使用者看不到網址列，無法確認是不是真的智生活，等於教使用者在別的網站輸入密碼。
  • 智生活改登入方式（OTP、驗證碼、MFA）時，每個嵌入的平台都要跟著發版。
  • 改用 iframe 也會被登入頁的 frame-ancestors 設定和瀏覽器的第三方 cookie 限制擋下。

為什麼登入後不把 token 存在瀏覽器

  • 用不到：綁定只需要 hash，而且走 S2S；⑨ 查資料用的也是 hash。
  • 風險跨平台：智生活的 token 放在行動客服的頁面上，行動客服一個 XSS 就能偷走智生活的 token。
  • 撐不久：token 會過期，綁定是永久的。

06綁錯人，等於帳號被接管

綁定表用 hash 查列，所以只要一列綁錯，從任一服務開 WebChat 都會查到錯的人。補綁流程要擋下面這些情境。

情境會發生什麼怎麼擋
冒用別人的 code攻擊者拿到別人的綁定 code，在自己的 WebChat 兌換；別人的 S1 被寫進攻擊者那一列，攻擊者就能透過 WebChat 讀別人的智生活資料。兌換時要出示 verifier，verifier 只存在發起綁定的那個 WebChat session；換到別的 session 就對不上 challenge。
塞入自己的 code攻擊者把自己的 code 塞進受害者的 widget，攻擊者的 S1 被寫進受害者那一列；之後攻擊者從智生活開 WebChat，會查到受害者那一列，讀到受害者在行動客服的資料。widget 只收自己開的彈出視窗、從該服務網域送來的訊息；就算塞進來，受害者 session 的 verifier 也對不上攻擊者的 challenge。
轉寄授權頁連結攻擊者用自己的 challenge 做出授權頁連結，傳給受害者登入；code 若交回攻擊者，受害者的 S1 就會寫進攻擊者那一列。授權頁只用 postMessage 把 code 交給開它的視窗，targetOrigin 固定為 WebChat 網域；code 不放進 URL；沒有開啟它的視窗就不寄放。
竄改要綁的對象如果網址帶著 P1 或 I1，改掉就能綁到別人身上。P1 從 WebChat 的 session 取得，只在後端之間傳遞，沒有參數可以改。
同一個 hash 綁進兩列同一個智生活帳號同時對應兩個人。IdP 綁定服務對每個服務欄位設唯一；衝突時拒絕綁定，不自動合併。

開場交接的 PKCE 可以照「內網 S2S 簡化版」延到 v2，但補綁的 verifier 比對 v1 就要有：補綁的 code 被冒用，後果是帳號被接管；而且授權頁本來就是新建的，多帶一個 challenge 成本很低。

07彈出視窗實作注意

  • 彈出視窗要在使用者點擊的當下開，否則會被瀏覽器擋。challenge 要先向 WebChat 後端拿，可以先開空白視窗，拿到 challenge 再導向授權頁；或在顯示「尚未綁定」時就先拿好。
  • widget 只收 event.source 是自己開的那個視窗、event.origin 是該服務網域的訊息；授權頁的 targetOrigin 寫死 WebChat 網域。
  • 授權頁不能設 Cross-Origin-Opener-Policy: same-origin，否則 window.opener 會被切斷，code 交不回 widget。宿主頁如果有設 COOP，也要實測 widget 開出的視窗還拿得到 opener。
  • 宿主頁若用 sandbox 嵌入 widget，要加上 allow-popups 和 allow-popups-to-escape-sandbox；少了後者，授權頁會繼承 sandbox 限制，登入表單可能無法運作。
  • 彈出視窗被關掉或逾時沒有結果時，widget 提示「未完成授權」，讓使用者重新走 ⑤。
  • App 的 WebView 不一定支援彈出視窗和 window.opener：App 要改用 iOS 的 ASWebAuthenticationSession、Android 的 Custom Tabs，導回方式另外設計。

08待確認

  • Token Exchange 服務改寄放會員 hash：不再寄放平台 token，「內網 S2S 簡化版」的存入／兌換合約要跟著改，並加上 challenge 欄位。
  • ⑨ 各服務 API 信任 WebChat 帶來的 hash：WebChat 的 API Key 等於能查任何人的資料，權限範圍與稽核要另外確認。
  • IdP 綁定服務的介面與權限：只開放 WebChat 後端以 API Key 呼叫查詢與寫入，寫入要留稽核紀錄。
  • widget 的 session cookie：widget 是嵌在別人網站裡的 iframe，它的 cookie 屬於第三方 cookie，Safari 預設會擋，開場和補綁都受影響；要確認做法，例如 Partitioned cookie，或把 session token 放在 widget 記憶體。
  • hash 演算法：必須固定不變，PK 或演算法一改，綁定就斷。PK 若是流水號，單純 SHA-256 一旦外流就能被窮舉回推，建議各服務用自己的密鑰做 HMAC。
  • 各服務新增 H(PK) 欄位：建唯一索引；既有會員要批次回填，新會員建立時一併寫入。
  • 綁定衝突：同一個 hash 已在別列時怎麼處理，之後要不要、怎麼合併兩列。
  • 解除綁定：使用者能不能自己解除，解除後要不要通知該服務。
  • App 內的補綁流程：WebView 不支援彈出視窗時的替代做法。
